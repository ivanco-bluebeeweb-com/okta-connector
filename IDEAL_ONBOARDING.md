# Okta Connector — идеальный первый запуск

Источник: `ONBOARDING_FIRST_LAUNCH_STANDARD.md`. Целевой пользователь: IT-администратор
или security engineer, впервые открывающий приложение.

## 1. Credential type
Okta org domain (`https://{yourOktaDomain}`) + один из двух режимов: API Token (SSWS)
или OAuth2 Service App (client credentials + private key JWT).

## 2. Идеальный флоу (без ограничений SDK)
1. **Явный выбор режима подключения** — переключатель "API Token" / "OAuth2 Service App"
   перед формой, так как поля принципиально разные (один секрет vs client id + приватный
   ключ), а не универсальная форма со всеми полями сразу.
2. **Проверка org домена и токена перед сохранением** — реальный запрос к `/api/v1/users/me`
   или `/api/v1/org` чтобы подтвердить домен и права разом, а не просто сохранить введённые
   данные вслепую.
3. **После успеха — сразу org health snapshot** — количество suspended пользователей,
   активных админов, и всплеск failed logins за последние 24ч из System Log, чтобы
   пользователь сразу увидел, что подключение реально работает и видит live-данные.
4. **Явное перечисление нужных OAuth scopes при выборе OAuth2-режима** — окта требует явный
   admin consent на конкретные scopes (`okta.users.manage`, `okta.groups.manage` и т.д.);
   идеально — показать чеклист "какие права нужны для каких функций" прямо в форме
   подключения, чтобы пользователь понимал, на что именно даёт согласие.
5. **Ошибки аутентификации — понятные, не generic 401** — например, если API Token
   истёк/отозван, явно подсказать создать новый в Admin Console > Security > API > Tokens,
   а не просто "unauthorized".
6. **Предупреждение перед деструктивными MFA/session-действиями** — reset_user_factors и
   clear_user_sessions должны показывать явное предупреждение "пользователь потеряет доступ
   ко всем текущим сессиям / будет должен переустановить MFA" перед выполнением, в идеале
   с двухшаговым подтверждением прямо в UI (не только в описании функции).
7. **Multi-org** — переключатель между несколькими подключёнными Okta-организациями
   (например, разные окружения клиента), с явным лейблом на каждой.

## 3. Разница с реализацией сейчас
См. `UI_COMPONENT_PLAN.md` §0 — реализация ограничена наличными примитивами SDK
(`ui.Select` для переключения режима подключения работает как переключатель полей формы,
но нет отдельного "preview consent" экрана — OAuth scope-чеклист описан текстом в форме
через `ui.Text`, а не как интерактивный чеклист с индивидуальными переключателями).
Двухшаговое подтверждение для reset_user_factors/clear_user_sessions реализовано через
стандартный `ui.Button` c `confirm=` параметром (native SDK confirm-dialog), что покрывает
идеал разумно близко.
